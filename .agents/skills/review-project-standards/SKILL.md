# 项目规范检查

## 原则

- 默认执行只读审查，不修改文件；只有用户明确要求修复后才改代码。
- 先读取并遵守适用的 `AGENTS.md`、README、项目约定、格式化配置、静态检查配置和测试命令。
- 先检查当日改动，再检查整体项目，两个范围分别报告。
- 以可复现证据为准，不把个人风格偏好当作缺陷，不为凑数量制造问题。
- 每个问题都说明原因、影响、整改步骤和验证方法，让用户能够自行完成修复。
- 不自动安装依赖，不执行会改写代码、锁文件、数据或外部系统的命令。

## 确定范围

1. 确认仓库根目录、当地日期、时区、当前分支和仓库状态。
2. 获取当天 00:00 至当前时间的提交及其 diff。
3. 获取暂存、未暂存和未跟踪文件；直接读取相关未跟踪文件。
4. 当仓库没有提交历史时，把工作区标为“当前工作区候选”，不能断言全部属于今日。
5. 将以上内容作为“当日改动范围”。
6. 将入口、目录结构、依赖与构建配置、路由、共享组件、核心业务层、数据访问、存储、任务、错误处理和测试作为“整体项目范围”。
7. 项目较大时优先检查高风险入口与跨层链路，并明确列出未覆盖区域，不能声称完成了全量检查。

## 执行检查

优先运行项目已经定义且不会改写文件的命令，例如编译、测试、静态检查或类型检查。缺少依赖、命令不存在或环境不满足时记录原因，不擅自安装或修改配置。

按代码实际包含的领域检查：

- 正确性：边界条件、空值、状态转换、错误分支、返回值、数据一致性和回归风险。
- 安全：输入验证、鉴权与授权、敏感信息、注入、路径穿越、上传、跨域、请求伪造和依赖风险。
- 目录结构：目录职责是否清晰，文件是否放在所属模块，是否存在重复入口、空占位目录、失效兼容层、命名错误和跨层反向依赖。
- 代码质量：单一职责、函数和文件复杂度、重复逻辑、死代码、隐式耦合、宽泛类型、可读性、可测试性、错误上下文和副作用边界。
- 后端：路由契约、中间件顺序、上下文传播、超时、并发、事务、幂等、资源释放、分层边界和错误映射。
- 前端：请求与错误状态、状态同步、渲染稳定性、交互反馈、语义化、键盘操作、可访问性、性能、组件职责、客户端与服务端边界以及逻辑复用。
- 工程化：依赖与配置一致性、构建可复现性、测试覆盖关键行为、日志可诊断性和文档与实现一致性。

代码质量问题必须给出具体证据，例如未引用文件、重复实现、错误依赖方向、同一组件承担多个独立状态流程、不可达分支或检查工具输出。不能只凭文件行数、个人审美或抽象偏好判定问题。

只有格式或命名违反仓库明确规则时才报告。不要建议与当前问题无关的重构、优化或技术替换。

## 判定严重程度

- `P0`：可直接造成严重数据损坏、远程利用、凭据泄漏或核心服务不可用。
- `P1`：高概率导致错误结果、安全边界失效、关键流程中断或严重回归。
- `P2`：在特定条件下导致功能、可靠性、性能、可访问性或维护问题。
- `P3`：影响有限但有明确规范依据和可衡量整改价值。

## 输出格式

先输出问题，再输出总结：

```markdown
## 当日改动检查

### [P1] 问题标题

- 位置：相对路径:行号
- 证据：可复现的代码行为或检查结果
- 原因：违反的项目约定或工程原理
- 影响：具体触发条件和后果
- 怎么改：按顺序给出最小整改步骤
- 怎么验证：给出测试场景或已有命令

## 整体项目检查

### [P2] 问题标题

- 位置：相对路径:行号
- 证据：可复现的代码行为或检查结果
- 原因：违反的项目约定或工程原理
- 影响：具体触发条件和后果
- 怎么改：按顺序给出最小整改步骤
- 怎么验证：给出测试场景或已有命令

## 检查总结

- 已检查范围：文件、模块和执行的命令
- 未覆盖范围：未检查区域及原因
- 检查结果：各严重程度数量
- 代码质量概况：目录边界、重复与死代码、复杂度、组件职责和可测试性
- 建议顺序：按照风险和依赖关系排列整改顺序
```

同一问题同时出现在两个范围时，在“当日改动检查”详细报告，在“整体项目检查”引用它，不重复整段内容。找不到问题时明确写“未发现可证实的问题”，同时说明检查范围和剩余风险。

## 教学整改

- 先解释触发问题的输入、状态或调用链，再解释规则本身。
- 整改步骤保持最小化，指出具体修改位置，不扩大到无关模块。
- 优先给测试思路和预期结果；用户要求代码时才提供最小代码片段。
- 提供代码时遵循仓库原有风格，不改名、不格式化无关代码、不删除原注释、不添加新注释。
- 区分必须修复、建议改进和无法确认的问题；证据不足时说明需要补充的日志、配置或运行条件。
